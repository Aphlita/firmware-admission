## 1. 为什么不能照旧公式字面实现

旧公式：

```text
U = [Σ未覆盖 w + Σ(E2/E3) w·(1−c)] / Σw
```

它把 E1 排除在两项之外，等价于 E1 贡献 0。但 `configs/judgement.yaml` 对 E1 的定义是
“在影子设备中成功启动，并通过实际请求-响应**复现该风险**”；`Evidence` 记录的也是
**阳性发现**（默认口令可登录、未授权接口、硬编码外联）。如果把 E1 算成 0，越确定的
高危问题反而越容易放行，三态会反向。

同时，`Evidence` 只有“发现”，没有“测了没问题”的状态；旧公式的 `未覆盖` 无法区分
“未测试”和“测过且干净”。因此 T2-1 需要显式的 `found / clear / not_tested` 三态。

## 2. 输入契约

- `CheckSpec`：来自 `configs/baseline.yaml` 的 9 个检查项，含 `code/severity/weight`。
- `Evidence`：每条阳性发现，含 `check_code/level/confidence`。
- `outcomes`：每个检查项的状态，取值只能是：
  - `found`：有证据，必须同时给出该检查项的 `Evidence`；
  - `clear`：本轮测试覆盖了该检查项且未发现风险；
  - `not_tested`：没有测试或测试不充分。
- 不传 `outcomes` 时，有 Evidence 的项记 `found`，其余记 `not_tested`：这是**保守默认**，
  不会把“没扫到”自动当成干净。

## 3. 风险与保障度

对每个检查项 i（权重 w_i）：

```text
risk_i =
  0                     status = clear
  w_i                   status = not_tested       # 未知按最坏情况
  w_i                   status = found 且 level = E1
  w_i * confidence_i    status = found 且 level = E2/E3

U = Σ risk_i / Σ w_i          # 0..1，越大越危险
```

保障度（这一项的证据有多“实”）：

```text
assurance_i =
  1.0                   status = clear
  0.0                   status = not_tested
  1.0                   status = found 且 level = E1
  confidence_i          status = found 且 level = E2/E3

A = Σ w_i * assurance_i / Σ w_i
```

为什么 E2/E3 用 `w * c` 而不是 `w * (1-c)`：`c` 是“这条发现为真的置信度”，
风险应当是 `w * c`；`w * (1-c)` 是残余不确定性，不是风险本身。

## 4. 三态判定顺序

按严重度从高到低，先硬规则、后加权阈值：

1. **硬拒绝**：任一 `Critical` 检查项出现 **E1** 发现 → `reject`。
2. **至少有条件**：任一 `Critical` 项出现 E2/E3 发现，或任一 `High` 项出现 E1 发现
   → 至少 `conditional`，不能直接 `pass`。
3. **证据不足**：`A < assurance_min`（默认 0.6）→ `conditional`；即使 U 看起来低，
   也不能因为“没测”而放行。
4. **敞口拒绝**：`A >= assurance_min` 且 `U > conditional_max`（默认 0.6）→ `reject`。
5. **敞口条件**：`U > pass_max`（默认 0.2）→ `conditional`。
6. 其余 → `pass`。

置信度：

- `pass`：`confidence = A`（保障度就是放行置信度）；
- `reject/conditional`：`confidence = max(A, 触发硬规则的最强证据 confidence)`，
  避免“红线命中但其他项没测”把置信度压到 0。

## 5. 边界行为（与测试一致）

| 输入 | U | A | 判定 | 理由 |
|---|---:|---:|---|---|
| 9 项全 `clear` | 0.0 | 1.0 | `pass` | 全部测过且未发现风险 |
| 9 项全 `not_tested` | 1.0 | 0.0 | `conditional` | 证据不足；不能放行，也不冒充“拒绝” |
| 9 项全 E3 发现（c=0.5） | 0.5 | 0.5 | `conditional` | Critical 项 E3 触发下限 + 保障度不足 |
| 1 个 Critical E1，其余 clear | 1/Σw | 1.0 | `reject` | Critical E1 硬红线 |
| 1 个 High E1，其余 clear | 0.8/Σw | 1.0 | `conditional` | High E1 至少条件放行 |

## 6. 对当前三锚点的含义

T1-2 的 A1/A2/A3 证据全部是 E3，**没有 E1/E2**。按本口径：

- 三台设备都不会直接 `pass`（A 低，且有 Critical 项的 E3 发现）；
- 也不会直接 `reject`（E3 不构成硬红线）；
- 结论应为 `conditional`，理由写明“静态证据、需影子设备复测”。

这正是本项目“不把静态推断冒充实测”的落点。要产出真正的 `pass` 与 `reject` 样例，
必须补：一台全项 clear 的干净固件，以及至少一台有 E1 实测的固件（FirmAE）。
